# Platfolio workspace mockup

This is the interactive draft of the public site, authentication and account flows, team workspace, template catalog, instance setup, environment management, and the instance lifecycle. See the [sitemap](../../sitemap.md) for route scope and the [UI guidance](../../ui-architecture.md) for layout and component constraints.

## Preview

From the repository root, run `node docs/design/mockup/serve.mjs`. Open [the fractalsynapse workspace](http://localhost:4173/dashboard/teams/fractalsynapse) to start as Adrian Webb. The preview binds to loopback. A narrow browser pane shows stacked panels. A wider pane places related cards side by side for comparison.

- **Workspace.** The Platfolio menu groups Home and Templates above the divider and Team workspace, Activity, Members, and Team settings below it. The Team selector opens the chosen workspace. The [team profile](http://localhost:4173/dashboard/teams/fractalsynapse) shows instances, captured deployment activity, and a timeline of hosting actions. Open the Activity tab to see the full timeline. Open an instance to see its environments and jump directly to Deployments, Configuration, or Domains. A breadcrumb on an environment page links back to the instance. Your teams and Invitations are in the avatar menu, where Invitations shows the pending count.
- **Authentication.** Hover over the user icon or open it by tap or keyboard, then choose Log out. Review branded sign-in, sign-up, password reset, and email verification with test values. Adrian's username is `adrianwebb` and his primary email is `adrian@example.test`. The mock links represent opening the recovery and verification emails.
- **Account.** Use Profile to edit username and display name or set a local photo. Use Emails to add and verify addresses and choose the primary address. Use Password to try the change form. Use Notifications to choose a verified destination for each team. Switch the primary or default address before removing it.
- **Teams and members.** Open Members or Team settings from the workspace or Platfolio menu. Team settings shows the stable URL Name first, followed by the editable Display name. In Members, try changing Morgan Lee's role or removing Jamie Chen. The last owner stays on the team.
- **External invitation.** In Members → Invitations, Active lists invitations awaiting a response. History keeps revoked, expired, and accepted entries. Each record shows when it was created and its email status. Try inviting `new-member@example.test`, then open the demo invitation from the email preview, create and verify an account, and accept from the user's Invitations page. To return as owner, log out and continue as Adrian.
- **Templates.** Open Templates from the home page or logo menu. Search by name, publisher, or capability, filter by category and operating mode, and sort by last updated or name. Compare the three published platforms and inspect their pinned source files. The team picker uses the same search and cards.
- **Instance setup.** In the team workspace, choose a template to open connections. Template details remain available from the catalog. Simulate GitHub App and Railway workspace access, select the demo targets, and name the instance. Set deployment branches and the starter's non-secret settings for each environment. The plan preview shows the proposed resources, credential requirements, and the install pull request handoff. The setup draft is held in memory until reload or sign-out.
- **Private Platfolio setup.** Open **Connections** on the team tabs. The cards follow the order an owner needs them in. Create the owner key, initialize and unlock OpenBao, connect Railway, and enter the sample marketplace code `demo`. The final link opens Starter Web setup. The files and access changes on this page are simulated.
- **Hub launch.** Open [Connections in hub mode](http://localhost:4173/dashboard/teams/fractalsynapse/connections?mode=hub) and review the private Platfolio installer card. The live button opens Railway. In the mockup it opens the owner’s Connections screen, where secret storage setup begins. Marketplace linking is a separate action in the hub.
- **Manage an environment.** Open the [platfolio instance](http://localhost:4173/dashboard/teams/fractalsynapse/instances/platfolio) to compare Production and Staging. Switch targets from inside either environment and use the Overview, Deployments, Configuration, and Domains tabs. Review a demo redeploy or see what the last deployment checks covered. Preview a sign-in provider change, set or replace a demo password or key by name and check the feedback on its row, or attach a demo domain and step through DNS and HTTPS verification. Demo changes are scoped to the target and reset on sign-out or reload.
- **App status.** Open Status on the platfolio app to review service checks and the full outage timeline. An owner can choose a name, brand color, and which production services to show, then preview and publish their status page at `/status/:team/:instance`. Public snapshots live in the same browser and stay available after reload. Unpublish to take the page down.
- **Notification rules.** Open Notifications from the user menu. Select a team, app, environment, and event. Use your default or another verified address. Rules can be edited, paused, resumed, or removed. This mockup saves rules for the session and sends no email.
- **Instance lifecycle.** Open Manage app on the hosted platfolio app. Review and simulate suspending and resuming managed compute in both environments. Download a sample configuration inventory and restore checklist. Review removal and type the instance name to confirm the demo handoff. Removal ends Platfolio management and preserves the stack in its current state. Open Removed apps from the team workspace to return to export and next steps.
- **Publish template.** Open Publish template in the team navigation. Use the platfolio source snapshot, describe the included materials, and preview the gradient card or add a cover image. The demo listing appears in Templates for the browser session, including its detail page and team picker.

A reload resets the walkthrough to its starting data, including lifecycle changes. The activity chart counts captured verification runs. The timeline labels session-only actions as Demo and clears them on sign-out. The lifecycle export contains sample inventory and restore steps. Sign-in, invitations, profile changes, and team creation are simulated in memory.

The mockup shares card surfaces, form controls, action styles, and spacing across routes. Deployment activity and app status use the same daily history and activity timeline in `activity-feed.mjs`. The history accepts a label, and each day supplies its description, tone, and bar size. Timeline entries can show tags, a time, a link, details, and inline controls such as outage updates. Category gradients distinguish template cards. Status colors identify states such as verified email and a passed deployment check. Exact states are also written in text.

The Account and authentication pages preview D69 and D70 in the [decision register](../01-product-and-decisions.md#decision-register). Keycloak remains the authority for sign-in and credentials. The prototype keeps verified notification addresses and team destinations separate from the sign-in address. It simulates email links and password submission locally. Test password values are discarded when forms are closed or submitted.

## Data and structure

`fixtures.mjs` includes the user-specified Adrian Webb, fractalsynapse team, and platfolio instance. The account identity, owner role, and Design review invitation are mock data. Production release `0.5.0` at `4942dd9` and the untagged staging build `36442bc` are recorded deployment check results from November 22, 2026. The snapshot timestamps use the capture files' modification times. Each run verified the candidate images, build identity, public status probes, database and site routes, and reported six passing identity protocol checks. See the [production release](https://github.com/fractalsynapse/platfolio/releases/tag/0.5.0) and [staging candidate PR](https://github.com/fractalsynapse/platfolio/pull/275) for provenance.

The fixtures contain only the fields displayed in the mockup. The site runs locally without provider requests. `mockup.mjs` holds the routes, shared page sections, and simulated account actions. `team-management.mjs` contains the team screens and local membership actions. `mockup.css` defines the mobile stack and wider workspace container. `serve.mjs` serves the static files and routes for local preview.

Team invitation creation, revocation and verified-address acceptance are described in the [OpenAPI contract](../../../apps/control-plane/openapi.yaml). Email previews do not contain an acceptance token. Display-name edits, roster reads, and changing or removing memberships are proposed contract work. See the [team wireframes](../wireframes/team.md) for the planned states.

The template cards use presentation snapshots of the [published catalog](../../../packages/manifest/src/template-catalog.ts). The starter listings show the source commit date. A demo listing shows when it was published and links to the pinned platfolio source. Actual instance setup will resolve and record its own source ref. The publisher preview simulates listing creation. See the [catalog wireframe](../wireframes/public.md#template-catalog) and [publisher wireframe](../wireframes/team.md#publish-template).

The setup flow is a local walkthrough using demo targets and template snapshots. Instance setup ends at plan review, before an instance record, install pull request, or provider deployment is created. The existing platfolio instance shows recorded deployment checks and its web addresses. Environment actions are simulated locally in `environment-management.mjs`. A redeploy stays Requested, an issuer edit creates a proposal, and secret delivery records demo presence without accepting a value. DNS records use sample values. See the [instance wireframe](../wireframes/instance.md) and [environment wireframes](../wireframes/environment.md).

This mockup uses sample service checks and outage reports on Status. Deployment checks are still recorded deployment evidence. There are no continuous probes, public hosting, or live outage alerts in the prototype.
