# 13 — Compose-first authoring, and who executes what

Two architecture principles, decided 2026-11-09. They change how a platform is **written** and who is
allowed to **act**, and they are recorded together because each constrains the other: Compose makes hosting
legible to developers, and the workflow split makes it safe to let developers' pipelines be the deploy path.

Accepted by the maintainer after the first real end-to-end deployment (`apps/status-api`, deployed by
`RailwayInfraProvider.applyPlan` and reachable over HTTPS). Step 7 is explicitly deferred to serve as the
test of this document rather than an example written to fit it.

## Principle 1 — Docker Compose is the authoring format

A platform is described by a **Compose document**, extended by platfolio semantics under `x-platfolio`.
Compose stops being something we emit and becomes something we read.

The reason is not elegance. Every hosted platform already has a Compose file for local development, and
today that file and our manifest are two descriptions of one system that drift. Compose is also the only
deployment format with a wide existing authorship — taking it as input means a tenant's existing file is a
starting point rather than a translation exercise, which is the whole import story.

### What the split looks like

| Concern | Owner |
| --- | --- |
| service list, image, `build`, ports, `environment`, named volumes, `healthcheck`, `depends_on`, resource limits, replica count | **Compose**, with its own meaning |
| which environments a service exists in, `ownership`, public hostnames, secret custody sources, identity/OIDC clients, DNS policy, lifecycle (`onSuspend`/`onEject`/`onDelete`), plan, release pinning | **`x-platfolio`** |
| dev vs prod shape | two documents merged by Compose's own `-f` rules |

`x-` prefixed keys are the specification's designated extension mechanism and are ignored by Docker, so a
platfolio file stays a Compose file — `docker compose up` is never a feature we have to re-earn.

### Generated, not hand-maintained

The dev and prod files are both **produced**, from one authored source:

- `compose.yaml` — what a person writes: services, `build:` contexts, local env, health, volumes.
- `compose.dev.yaml` — local: builds from source, host ports, no pins, non-persistent volumes allowed.
- `compose.prod.yaml` — remote: `image: registry/repo@sha256:…` for every service, no `build:`, managed
  resources marked as such, limits from the plan.

Nobody maintains the prod file by hand, which is the point: it is regenerated by the release pipeline after
it builds and pins images, and the drift gate is simply *regenerate and compare*. A hand-edited prod overlay
is a pinned image the release job did not build — the same class of failure as a mutable tag, and caught the
same way.

This is what makes local and remote one architecture rather than two: a `postgres` or `keycloak` service is
declared once, runs as a container locally, and is merged with the remote equivalent — managed database via
the provider's template path, or a plain external service — without the developer writing a second spec.

### The supported subset, and refusals

We support a documented subset and refuse the rest with named codes. Generous in, strict in what maps: an
importer that quietly drops a field produces a system that runs differently from the file the tenant read.

Accepted service keys: `image`, `build` (dev only), `command`, `environment`, `expose`/`ports` (first
container port becomes the service port), `healthcheck`, named-volume `volumes`, `depends_on`,
`deploy.resources.limits`, `deploy.replicas`, `labels` (ignored), `networks` (names only), `working_dir`.

Refused, with the reason in the message: `env_file` and top-level `secrets`/`configs`; `build` in a prod
overlay; `network_mode`, `privileged`, `cap_add`, `security_opt`, `pid`, `ipc`, `tmpfs`, `devices`,
`device_requests`, `runtime`, `ulimits` and `sysctls` beyond the documented set; bind mounts (host paths);
`external` networks with driver options; `extends`; `include` (we merge documents ourselves so the set of
files stays explicit in platfolio's record); `deploy.placement`, `deploy.update_config` beyond
`replicas`; any interpolation whose default could carry a secret value.

`env_file` and `secrets` are the real collision and they are refused on principle rather than implemented
badly: Compose's convenience is that values arrive from a file at run time, and platfolio's invariant is
that a secret is a **name with a declared source** which the control plane may not read. Interpolating
values from a tenant's `.env` into state would make us a secret store with extra steps. The importer says
what it cannot express, and offers the equivalent: names in `x-platfolio.secrets`, values supplied by the
tenant.

### Importing an existing repository

A repo arrives with `docker-compose.yml`, sometimes two or three files, sometimes a Makefile. Import is
therefore a **report first, plan second**: parse, merge, map what maps, and list exactly what will behave
differently hosted — every refusal, every bind mount, every `env_file`, every service with no health check,
every managed-vs-container assumption. A tenant confirming "no A records, apex needs flattening" is a better
first interaction than a deploy that fails for a reason three layers away. Bind-mounted data has no hosted
equivalent and must never be silently converted into a named volume.

The catalog keeps shipping generic reference manifests only (D28), which compose-first makes easier: an
example is a Compose file plus a small `x-platfolio` block, and a real platform's file is the same shape.

## Principle 2 — platfolio is the actor, the tenant's pipeline is the executor

`D22` already made GitHub workflows the execution plane. This makes the division explicit, because "put it
in CI/CD" hides a decision about who can change a running system.

| | platfolio control plane | tenant's GitHub workflows |
| --- | --- | --- |
| decides what version should run | yes, from intent, plan and billing state | no |
| applies app deployments | triggers, does not perform | yes — runs with the tenant's grants |
| observes state | yes, provider read APIs, polled | reports back through status/metadata |
| enforces lifecycle (suspend, scale-to-zero, restore) | yes, through its managed grant | no |
| holds the provider credential | tier-dependent, per D24 | the runner does, at run time |

The seam is `workflow_dispatch`: platfolio **starts** a curated workflow rather than doing the tenant's
mutation itself, so the tenant's pipeline stays the path of record and the audit trail is a GitHub tab
instead of something we build and defend.

That split answers the tension in "everything through workflows": if the only way to change a tenant's
stack were their pipeline, then disabling Actions would disable platfolio's authority — including
suspend-for-non-payment and restore-from-backup, which cannot depend on tenant goodwill. So the rule is
**deploys through git, lifecycle through the managed grant**, which is the tier shape accepted in D24
rather than a new exception.

### Four laws, because each was already paid for in measurement

1. **A secret is written once and never read back.** platfolio is the management interface, so it *must* be
   able to set a workflow secret the tenant just supplied: `PUT …/actions/secrets/NAME` with the value from
   that request. What is forbidden is storage and retrieval. GitHub makes retrieval structurally impossible —
   the API is write-only, and presence is checkable (`GET` → 204 present, 404 absent). Railway is the
   opposite: its variables **are** readable, which is why the provider reads keys only and why that
   constraint is behavioural rather than enforced by the platform. So the rule is directional:
   **tenant → platfolio → the tenant's execution plane, once, in memory, never persisted, never fetched
   again.** No logs, no database column, no cache, no plan artifact, no value in a Compose file or the
   repository.
   
   The consequence belongs in the UI, not just here: **write-once means re-apply cannot re-deliver a lost
   secret.** If a value was set and then deleted upstream, the action is rotate-and-rebind, never replay —
   because there is nothing stored to replay. Caching it to make retries convenient would be the easiest
   way to break the invariant from the inside.
2. **Workflow logs are never read.** They are free text and routinely contain resolved environment values.
   Run *status* is metadata; a diagnosis comes back as a structured field the workflow chose to emit.
3. **A pinned image means the release job built it.** A digest that the pipeline did not produce is not
   evidence of anything, which is the same objection that keeps Railway-from-repo builds out of the default
   path: it produces an artifact our release job did not sign (D16).
4. **Curated workflows are shipped as PRs and pin actions by commit SHA.** We author code that runs with a
   tenant's privileges, so mutable tags on someone else's action are our supply chain, and pushing into their
   repo is a boundary we already declined (D22). Drift detection covers tenants editing what we wrote, and
   import has to cope with the deploy pipelines a repo already had.

### Runners

GitHub-hosted runners stay the default: ephemeral per job, the tenant already pays GitHub for minutes, and
no platfolio machine ever sees a tenant secret. We will not operate a runner fleet — the objection is not
cost but boundary: a runner checks out the tenant's code and runs their build with their secrets, so a shared
fleet puts every tenant's secrets on our hardware and every other tenant's jobs beside them.

What we may offer, and the maintainer accepted only in this form: **a runner hosted inside the tenant's own
account, as a managed service** — we install and operate it, the isolation is theirs, and it is priced as
management, which is the product. Nothing may depend on it; if the option disappears the workflow path is
identical.

## What this changes in the code we have

`packages/manifest` already renders Compose, so the format is known to the system; the inversion is to read
it. The plan of record:

1. **Compose as an input adapter** into the existing intermediate model — not a parallel pipeline. Compose
   in, same validation, same renderers, same `buildPlan`, same provider. That keeps `02`'s architecture and
   makes step 7 the test instead of the exception.
2. **Overlay generation**: `compose.dev.yaml` and `compose.prod.yaml` produced from the authored document
   plus the release pipeline's pinned images, with regenerate-and-compare as the gate.
3. **Importer report** before plan, refusing loudly.
4. **Presence checks, not secrets writes** for the Actions path, and structured workflow outputs.
5. Existing `railway.json`/`railway.toml` stays retired; IaC output remains an ejection artifact, not the
   execution mechanism, for the reason measured in E24: `environmentApplyChangeSet` answers `applied` to any
   payload. Compose is the authoring format precisely because the *provider's* API is still the executor.

## The environment inventory: what a platform needs, not what it holds

Compose and the manifest describe **topology**. Neither describes **obligations** — which variables a build
requires, which are secrets, what the defaults are, where a value comes from, and whether a missing one is
fatal or merely unoptimised. Without that, "is this instance ready to deploy?" is unanswerable and the
onboarding checklist gets invented per platform. So the model gains an inventory, authored in the platform's
own repository and built up over time:

```yaml
# .platfolio/environment.yaml (or x-platfolio.environment inside the Compose document)
- name: DATABASE_URL
  kind: reference            # resolved by the provider; never a value here
  service: web
  environments: [production, staging]
- name: APP_API_SIGNING_KEY
  kind: secret
  required: true
  rotate: on-demand
  description: Signs bearer tokens issued by the API.
- name: CONTEXT_BUDGET_TOKENS
  kind: value
  default: "120000"
  environments: [production]
- name: OIDC_ISSUER
  kind: output               # supplied by another instance; see the next section
  from: team-service/oidc#issuer
```

`kind` is the load-bearing field, and it replaces today's split between `env` (values) and `secrets` (names),
which cannot express a default, an applicability range, or "this comes from a service". The rules that make it
safe:

- **A `secret` entry never carries a value anywhere in the repository.** The value exists only inside the
  request that writes it into the tenant's execution plane. Names, descriptions and defaults are inventory;
  the value is not data platfolio may hold.
- **A `value` entry may carry defaults** — that is the point — and anything resembling a credential in one is
  refused by the existing placeholder scan, escalated from a warning to a hard refusal for inventory files.
- **`reference` and `output` entries are wiring, not obligations**, so they never appear on the panel that
  tells a tenant what to supply. That distinction came out of #84 at the plan layer; it belongs at the
  authoring layer too.
- **Absence is a state, not an error.** The panel reports `missing / set / set-but-unverifiable`, because we
  can confirm presence for workflow secrets and confirm nothing about a Railway variable without reading its
  value, which we will not do.

This is where `platform-text.yaml`'s placeholder policy and the page-schema secrets panel finally meet: one
file answers what a platform needs, what a tenant is asked for, and what must never be committed.

## Feeding one platform's outputs into another's inputs

Independent instances have to interoperate: a team-run identity service whose issuer and client credentials
a hosted platform consumes; shared logging endpoints; a backend API several platforms call. Plan-level
`references` only reaches a database inside the same environment, which is too small. This is OD11's S2
shape, and the requirement that **management-layer services produce inputs for dependent platforms** is what
makes it concrete rather than speculative.

Three things, and only three:

- **`provides:`** on a team-service instance, naming typed outputs — `issuer` (public URL), `jwks_uri`,
  `api_base`, or `client_secret` (**generated, single-use**).
- **`requires:`** on a dependent instance, referring to a *capability* rather than a resource: "I need an OIDC
  provider", not "I need `plat/inst-a1`" — so a team can swap the supplier without editing dependents.
- **Binding**, which resolves requires against provides inside a team and writes the results into the
  dependent: public values into variables, credentials through the write-once path above.

Two consequences to settle on the record rather than discover in production:

1. **A generated credential cannot be re-delivered.** If the identity service mints a client secret and
   platfolio relays it once, a failed apply cannot replay it — nothing was kept. So binding must be
   **re-issue, not retry**: the dependent's action is "rotate at the supplier and rebind", which the UI has to
   offer as a workflow rather than surfacing an error string.
2. **Bindings must survive supplier changes.** A changed issuer URL means every dependent needs a fresh write,
   and dependents run on their own release cycles. A binding therefore records the *generation* it was
   satisfied against, so the UI can say "two of three consumers are still pointed at the old issuer" — the same
   honest-pending discipline as the DNS checklist in [12](12-domains-and-dns.md).

Public values crossing an instance boundary are unremarkable; an issuer URL is advertised. Credentials
crossing it are the interesting case: **relay once, persist never, re-issue on demand** — the same rule as a
tenant's own secrets, with the supplier rather than the tenant as the origin.


## Consequences to watch, stated now

- Compose is a moving target across spec revisions and tool versions: the accepted-subset list needs a
  version marker, and the refusal codes are the compatibility surface.
- Local container versus managed remote service is a real behavioural difference (backups, PITR, password
  rotation, connection limits). The interface is shared; the guarantees are not, and the UI has to say so.
- `depends_on` is not placement or replication semantics, and must never be read as such on the provider
  side.
- Two descriptions of one system remain possible if someone edits `compose.prod.yaml`; the drift gate is the
  answer, and it only works if the prod file is generated.
