## 1. Stripe Billing architecture for "purchase → provision, cancel → deprovision"

### 1.1 Objects and the recommended entry point

**VERIFIED** — [How the Billing APIs work](https://docs.stripe.com/billing/billing-apis) defines the object set a subscription connects: `Product`, `Price`, `Customer` (or customer-configured **Account** in the Accounts v2 API), `Subscription`, `Invoice`, `PaymentIntent`, `PaymentMethod`, `Entitlement`, `Feature`, `ProductFeature`. Stripe states the recommendation verbatim: *"We recommend using the Checkout Sessions API to create subscriptions"* and *"For most use cases, we recommend modeling your customers as customer-configured Account objects instead of using Customer objects"* (Accounts v2: GA for Connect users, public preview for others).

**VERIFIED** — [`POST /v1/checkout/sessions`](https://docs.stripe.com/api/checkout/sessions/create) parameters seen in the API reference and the OpenAPI spec:

| field | what it does |
| --- | --- |
| `mode` | enum `payment` \| `setup` \| `subscription`; "Pass `subscription` if the Checkout Session includes at least one recurring item." |
| `line_items[]` | `{price, quantity}`; subscription mode max **20 recurring line items + 20 one-time** (one-time items bill on the initial invoice only) |
| `client_reference_id` | *"A unique string to reference the Checkout Session… can be a customer ID, a cart ID, or similar, and can be used to reconcile the session with your internal systems."* → put your **tenant id** here |
| `metadata` / `subscription_data.metadata` | free-form key-value, propagated to the Subscription |
| `subscription_data.*` | `trial_end`, `trial_period_days`, `trial_settings.end_behavior.missing_payment_method` (enum `cancel` \| `create_invoice` \| `pause`), `billing_cycle_anchor`, `billing_mode`, `proration_behavior` (`create_prorations` \| `none`), `default_tax_rates`, `transfer_data`, `application_fee_percent`, `on_behalf_of` |
| `consent_collection.terms_of_service` | enum `none` \| `required` → ToS checkbox enforced at checkout |
| `automatic_tax.enabled`, `tax_id_collection`, `billing_address_collection`, `customer_creation`, `phone_number_collection`, `custom_fields` (≤3), `success_url` / `cancel_url`, `expires_at` (30 min – 24 h, default 24 h), `ui_mode` (`hosted_page` default, `embedded_page`, `form`, `elements`) | |

**INFERENCE (recommended wiring)** — `checkout.session.client_reference_id = platfolio tenant id`; `subscription_data.metadata = {tenant_id, plan_key}`; keep `Price → plan_key` in your own table (see §2). Persist `customer`, `subscription`, `latest_invoice` from the event payload.

### 1.2 Lifecycle / webhook contract

**VERIFIED** — [Using webhooks with subscriptions](https://docs.stripe.com/billing/subscriptions/webhooks) event table:

- `customer.subscription.created` (status may be `incomplete` if `payment_behavior=default_incomplete`), `.updated`, `.deleted` ("Sent when a customer's subscription ends"), `.paused`, `.resumed`, `.trial_will_end` (**sent 3 days before trial ends**; also fires if the trial is shorter than 3 days)
- `invoice.paid` — *"You can provision access to your product when you receive this event and the subscription `status` is `active`."*
- `invoice.payment_failed`, `invoice.finalized`, `invoice.finalization_failed` (inspect `Invoice.last_finalization_error`, `automatic_tax.status` = `requires_location_inputs`), `invoice.upcoming` (a few days before renewal, configurable in Dashboard; **not sent** when `collection_method=send_invoice`), `invoice.created` (handle `automatic_tax[status]=failed` by retrying), `invoice.updated` (carries `next_payment_attempt` for automations users)
- `entitlements.active_entitlement_summary.updated` — *"When you receive this event, you can provision or de-provision access to your product's features."*
- risk/data events you should not skip: `charge.dispute.created`, `charge.refunded`, `radar.early_fraud_warning.created`, `customer.updated`
- `subscription_schedule.*` (incl. `subscription_schedule.aborted` — "canceled because payment delinquency terminated the related subscription")

**VERIFIED** — reliability rules from [Webhooks](https://docs.stripe.com/webhooks): *"Stripe doesn't guarantee the delivery of events in the order that they're generated"*; *"Track event IDs to identify duplicate deliveries"*; dedupe using `event.id` (and, for two distinct Event objects, `data.object` id + `event.type`); *"return a `200` response before any complex logic"*; process events through an **asynchronous queue**; verify `Stripe-Signature` with the raw body. From the subscription webhooks page: in live mode *"Stripe continues retrying the webhook notification for up to 3 days with an exponential back off"* (sandbox: 3 retries over a few hours).

**VERIFIED (Stripe's own recommended flow)** — [Build a subscriptions integration](https://docs.stripe.com/billing/subscriptions/build-subscriptions) ("Provision and monitor subscriptions"): *"After the subscription signup succeeds, the customer returns to your website at the `success_url`, which initiates a `checkout.session.completed` webhook. When you receive a `checkout.session.completed` event, **use entitlements to provision** the subscription. Continue to provision each month … as you receive `invoice.paid` events. If you receive an `invoice.payment_failed` event, notify your customer and send them to the **customer portal** to update their payment method."* Also: *"After receiving `invoice.paid`, retrieve the associated subscription and confirm that its status is `active` before extending the customer's access expiration date. A paid invoice doesn't necessarily transition the subscription to `active` when status resolution uses all invoices."*

### 1.3 State machine, dunning, and how long to keep a tenant in `past_due`

**VERIFIED** — [How subscriptions work](https://docs.stripe.com/billing/subscriptions/overview): `Subscription.status` enum `incomplete`, `incomplete_expired`, `trialing`, `active`, `past_due`, `canceled`, `unpaid`, `paused` (also confirmed from the OpenAPI spec for the subscription object).

- First payment: *"the customer must make a successful payment within **23 hours**"*; after 23 h the subscription becomes `incomplete_expired` and the invoice becomes **void** — *"create a new subscription for them"*. For `collection_method=send_invoice`, *"Stripe creates an invoice with the status `open` … subscription status is `incomplete`"* and Stripe e-mails a hosted invoice link with a configurable due date.
- *"Smart Retries and custom retry rules don't retry the initial payment while the subscription is `incomplete`"* → your integration must collect the first payment itself.
- `past_due`: *"Stripe might retry payment while the subscription is `past_due`, but this status doesn't guarantee another payment attempt. Your Dashboard subscription settings determine the subscription's next status. If an invoice is still unpaid after all payment retries, you can configure the subscription to move to `canceled` or `unpaid`, or to remain `past_due`."*
- `unpaid`: *"Revoke access to your product when the subscription is unpaid because Stripe already attempted and retried payment while the subscription was `past_due`."*
- During `unpaid`: *"The subscription continues to generate invoices but doesn't attempt payment"* (invoices stay in **draft**).
- `canceled` is terminal; during cancellation Stripe sets `auto_advance=false` on unpaid invoices.
- ACH-type payment methods that can't return status immediately *"can move directly to `active` after creation and bypass `incomplete`. If the payment fails later, Stripe voids the invoice but the subscription remains `active`"* → design access control accordingly.

**VERIFIED** — [Automate payment retries / Smart Retries](https://docs.stripe.com/billing/revenue-recovery/smart-retries): *"For new Stripe accounts, Stripe enables Smart Retries by default and configures it for **up to 8 retries within 2 weeks**."* Configurable retry count within a period of **1 week, 2 weeks, 3 weeks, 1 month, 2 months**. Custom rules: *"up to three retries, each with a specific number of days after the previous attempt."* Fields: `invoice.attempt_count`, `invoice.next_payment_attempt` (moved to `invoice.updated` for Automations users). Hard-decline codes that block auto-retry (`incorrect_number`, `lost_card`, `pickup_card`, `stolen_card`, `revocation_of_authorization`, `revocation_of_all_authorizations`, `authentication_required`, `highest_risk_level`, `transaction_not_allowed`). Post-recovery outcomes (Dashboard, "Manage failed payments for subscriptions"): *Cancel the subscription / Mark the subscription as unpaid / Leave the subscription past-due / Pause the subscription*; *"After the final payment attempt, Stripe makes no further payment attempts."* Direct-debit retry caps: ACH 2/40 days, SEPA 2/30 days, Bacs 2/30 days, BECS(AU) 4/30 days, CAD 1/30 days, NZ 1/30 days.

**VERIFIED** — [Automatic collection](https://docs.stripe.com/invoicing/automatic-collection): for `send_invoice` invoices, *"Change a past due invoice's status — You can mark an invoice as uncollectible if it's past due by **30, 60, or 90 days**"*; "Email finalized invoices to customers"; auto-reconcile partial payments within a configured minimum; automatic reminders before/on/after the due date.

**INFERENCE — recommended platfolio state machine** (aligned to the above):

```
none → pending_checkout            (Checkout Session created, client_reference_id=tenant)
     → provisioning      ← checkout.session.completed + subscription.status ∈ {trialing, active}
                          (or invoice.paid + status=active)
     → active            ← invoice.paid / entitlements.active_entitlement_summary.updated
     → grace (past_due)  ← invoice.payment_failed; keep tenant running, show banner,
                            e-mail + Customer-portal link; do NOT self-retry billing
     → suspending (unpaid or cancel_at_period_end reached) ← customer.subscription.deleted /
                            status=unpaid: stop new ops, scale workloads to zero, keep data
     → eject_period      (data export window; see §6)
     → deprovisioned     (delete after documented retention; invoice.finalization/void handled)
```
Given Stripe's own defaults (8 retries / 2 weeks) and its "revoke access when `unpaid`" instruction, **~14 days of `past_due` + a short `unpaid` grace (7–14 days) then suspend-then-delete (30 days total post-termination)** is defensible; anything much longer means you are subsidising runaway infra you can't recover cost on.

### 1.4 Trials, free tier, plan changes, proration

**VERIFIED** — [Configure trial offers](https://docs.stripe.com/billing/subscriptions/trials): Stripe is moving trials to a **Trial Offer API** (`product-catalog/trial-offer/create`, params `price` (0 USD ⇒ free trial), `end_behavior.transition.price`, `nickname`). Requires Stripe API version **`2026-09-30.endive` or later** and **`billing_mode=flexible`** on the subscription. Use-case table: discounted trials, free trials (a 0 USD item), upgrade trials, item-level trials. *"You can't use trial offers and the legacy `trial_end` parameter together."* Trial offers are **not** supported with Payment Links, pricing tables, or Checkout outside a **private preview**. Portal: *"you can use the customer portal to view and cancel trial offers… You can't update, pause, or resume subscriptions with trial offers."* Free/paused behaviour: `trial_settings.end_behavior.missing_payment_method` = `pause` (→ `customer.subscription.paused`) or `cancel` (→ `customer.subscription.deleted`); *"Trial offers have the same limitations as legacy free trials with no payment method, including the limitation that **metered items aren't supported**"*; `trial_settings.end_behavior.billing_cycle_anchor` configurable (`unchanged` etc.); *"customer modifications to a `trialing` subscription end the free trial and create an invoice for immediate payment"* unless portal config sets `features.subscription_update.trial_update_behavior=continue_trial`.

**VERIFIED** — legacy trial params on `POST /v1/subscriptions`: `trial_end` (*"Can be at most two years from `billing_cycle_anchor`"*; special value `now` ends the trial immediately), `trial_period_days`, `trial_from_plan`. Subscription object exposes `trial_start`, `trial_end`, `trial_settings`.

**VERIFIED** — [Prorations](https://docs.stripe.com/billing/subscriptions/prorations): `proration_behavior` enum `always_invoice` | `create_prorations` (default) | `none`; `proration_date` lets you apply the same time you previewed with `invoices/create_preview`; *"Negative prorations aren't automatically refunded and positive prorations aren't immediately billed"*. Identification: `invoiceitem.proration` or `invoice.parent.subscription_item_details.proration`. Table of what Stripe counts as a proration (credits, backdated periods, partial-period debits, `cancel_at`-shortened renewal = true; full-period debits at creation, trial start/end, regular renewal = false).

**VERIFIED** — [classic vs flexible billing mode](https://docs.stripe.com/billing/subscriptions/billing-mode/compare): *"You can't migrate a subscription from flexible billing mode to classic billing mode."* Flexible: credit prorations computed from the **original debit**; discounts applied **proportionally per item**; metered items excluded from the first invoice (no 0 USD line); *"charges for usage based on the price that was in effect when the usage was reported, rather than the most recent price"*.

**VERIFIED** — [Cancel subscriptions](https://docs.stripe.com/billing/subscriptions/cancel): `DELETE /v1/subscriptions/{id}` (immediate by default), `cancel_at_period_end=true` (reversible until period end), `cancel_at` (custom date; changing it inside the period creates prorations), `prorate` + `invoice_now` on cancel, and the sharp edge: *"If you don't prorate the subscription, **all metered usage gets discarded** and the customer won't receive credit for any potential prorations."* Dispute-driven choice: *"Cancel the subscription at the end of the period … allows you time to work through the dispute process before the cancellation occurs."*

**VERIFIED** — [Customer portal](https://docs.stripe.com/customer-management): self-serve payment-method update, invoice history, plan switching (**max 10 products** in the allowed list), cancellation page with *cancellation deflection* coupons + reason capture, pause/resume, `features.subscription_update.trial_update_behavior`; *"If you're using the customer portal with Stripe Connect, configure the customer portal for the platform instead of a connected account."*

## 2. Entitlements — Stripe has a first-party product here

**VERIFIED** — Stripe Billing **Entitlements** exists and is documented, with an API:

- Guide: [Entitlements](https://docs.stripe.com/billing/entitlements) — *"An entitlement represents a customer's access to a feature. When a customer purchases or subscribes to a product with an attached feature, Stripe creates and manages an **Active Entitlement** for that customer and feature."* Setup is Dashboard-first: *Product catalog → **Features** → Create feature* with a **`Name`** and a **`Lookup Key`** (unique; reusable only after the feature is archived), then **Attach to product**. *"When a customer's subscription is first activated, Stripe creates entitlements for the features that they're subscribed to."* Caveat: *"Existing subscriptions will create active entitlements for any product feature changes at the start of the next billing period."* Archival: archived features still create entitlements if attached to existing products; **you can't unarchive**; the lookup key becomes reusable.
- API reference: [The Active Entitlement object](https://docs.stripe.com/api/entitlements/active-entitlement/object) — `id`, `object: "entitlements.active_entitlement"`, `feature` (expandable), `lookup_key` (≤80 chars), `livemode`. [List all active entitlements](https://docs.stripe.com/api/entitlements/active-entitlement/list) — `GET /v1/entitlements/active_entitlements?customer=…` (`customer` **required**). [Create a feature](https://docs.stripe.com/api/entitlements/feature/create) — `POST /v1/entitlements/features` with `name`, `lookup_key`, `metadata`; example request uses header `Stripe-Version: 2026-10-28.endive`.
- OpenAPI spec paths ([stripe/openapi](https://raw.githubusercontent.com/stripe/openapi/master/openapi/spec3.json)): `/v1/entitlements/features` (get, post), `/v1/entitlements/features/{id}` (get, post), `/v1/entitlements/active_entitlements` (get), `/v1/entitlements/active_entitlements/{id}` (get). **No POST on active_entitlements** → active entitlements are created by Stripe from subscription/purchase, not by you.
- Event: `entitlements.active_entitlement_summary.updated`.
- Object model also includes `ProductFeature` (feature↔product join) and Billing APIs page lists `Entitlement` and `Feature` as first-class resources; the [iOS subscription doc](https://docs.stripe.com/billing/subscriptions/manage-ios) references retrieving active entitlements.

**UNVERIFIED** — (a) whether Entitlements works with **Connect** connected accounts or only with `Customer` (the list endpoint keys on `customer`), (b) whether the **Accounts v2** customer-configured Account is accepted in place of `customer`, (c) hard GA vs beta status (docs show no beta banner; API examples carry an `endive` version header), (d) whether a purchase (non-subscription) creates entitlements — the billing-apis page says entitlements are created *"when you create a subscription for a customer's recurring purchase of a product"*.

**Recommendation (INFERENCE)** — use Stripe as the *authority for "which feature keys this tenant has"*, not for numeric limits. Model: one `Feature` per capability (`railway-provisioning`, `managed-migrations`, `priority-support`, `multi-env`, `white-label`), one `ProductFeature` per plan product, and a small local table `feature_lookup_key → limits/quota` (max services, RAM, seats). Then your control plane resolves access only via `GET /v1/entitlements/active_entitlements` + the `entitlements.active_entitlement_summary.updated` event, which gives you a *single* provisioning/re-provisioning trigger instead of re-deriving plans from `Price.id` in every code path. Keep a cached copy (Stripe is your source of truth, but you need offline enforcement and an audit trail of *why* something was deprovisioned).

## 3. Usage-based / metered billing — important change in Stripe's guidance

**VERIFIED (headline)** — Stripe now positions **Metronome** (acquired; "Metronome is now part of Stripe") as *"Stripe's primary usage-based billing platform and the recommended starting point for all new integrations"*, while **Billing Meters** is *"a lower-level primitive that remains fully supported for existing integrations"*. Source: [Basic usage-based billing](https://docs.stripe.com/billing/subscriptions/usage-based) and the implementation guide, which carries an explicit **"Not Recommended"** callout for new Meters integrations ([Set up a pay-as-you-go pricing model](https://docs.stripe.com/billing/subscriptions/usage-based/implementation-guide)).
Compatibility matrix ([Compare basic usage-based billing and Metronome](https://docs.stripe.com/billing/subscriptions/usage-based/compare-metronome)): Meters = ✓ Checkout, ✓ **Connect**, ✓ Adaptive Pricing, ✓ Workflows, ✓ Stripe Dashboard, ✓ Automatic Tax; Metronome = ✗ Connect, ✗ Adaptive Pricing, ✗ Workflows, ✗ Dashboard, **limited Checkout** ("requires custom API calls and webhook configuration"), ✓ Automatic Tax. Meters weaknesses: *"Billing Meters only updates at invoice time"*, *"High-volume event ingestion: Limited"*, *"Credits are only reconciled at invoice time. Customers can exceed their balance during the cycle"*; no prepaid drawdown / commits / ramp schedules / dimensional pricing.

**VERIFIED — the objects to use if you stay on Stripe-native Meters** (API reference pages `api/billing/meter*`):

- `POST /v1/billing/meters` → `billing.meter` fields `display_name` (≤250), `event_name` (≤100), `default_aggregation.formula` = `sum` | `count` | `last`, `customer_mapping.type` = `by_id` with `customer_mapping.event_payload_key` (default `stripe_customer_id`), `value_settings.event_payload_key` (default `value`), `event_time_window` = `day` | `hour` (pre-aggregation), `status`, `status_transitions.deactivated_at`. Lifecycle endpoints: `/deactivate`, `/reactivate`; summaries: `GET /v1/billing/meters/{id}/event_summaries`. Events: `billing.meter.created|updated|deactivated|reactivated`.
- Metered **Price**: `POST /v1/prices` with `recurring[usage_type]=metered`, `recurring[interval]=month`, `recurring[meter]={{METER_ID}}`, `billing_scheme=per_unit`, `unit_amount`, `transform_quantity[divide_by]` + `[round]` (e.g. 0.04 USD per 100 units), or `billing_scheme=tiered`/`tiers_mode`.
- `POST /v1/billing/meter_events` → `billing.meter_event` fields `event_name`, `payload`, `identifier`, `timestamp`. **Gotchas verbatim**: `identifier` — *"If not provided, one is generated. We recommend using UUID-like identifiers. Stripe enforces uniqueness within a rolling period of at least 24 hours."*; `timestamp` — *"Must be within the **past 35 calendar days** or up to **5 minutes in the future**. Defaults to current timestamp if not specified."*
- Async aggregation: *"Stripe processes meter events asynchronously, so aggregated usage in meter event summaries and on upcoming invoices might not immediately reflect recently received meter events"* ([Record usage for billing](https://docs.stripe.com/billing/subscriptions/usage-based/recording-usage)).
- Reporting: `billing.meter_event_summary` (`aggregated_value`, `start_time`/`end_time` aligned to minute boundaries) via `GET /v1/billing/meters/{id}/event_summaries` with required `customer`, `start_time`, `end_time` and optional `value_grouping_window` = `day` | `hour`.
- Corrections: `POST /v1/billing/meter_event_adjustments` — `type=cancel`, `cancel[identifier]=…`; *"Time period cancellation is **not supported yet**."*
- Credits/alerts: `/v1/billing/credit_grants` (create/get/update/expire/void) + `/v1/billing/credit_balance_summary`, `/v1/billing/credit_balance_transactions` (in the OpenAPI spec); usage-threshold alerts via `/v1/billing/alerts` ([Monitor usage](https://docs.stripe.com/billing/subscriptions/usage-based/monitor)); bulk ingest: CSV upload in Dashboard, or **Amazon S3** ([docs links on the recording-usage page](https://docs.stripe.com/billing/subscriptions/usage-based/recording-usage)).
- Billing in arrears is inherent: *"Pay-as-you-go pricing lets you charge customers in arrears for the usage they accrue. Customers pay only for what they consume, and you invoice them at the end of each billing interval."*
- Legacy model still documented at [usage-based-legacy (Usage Records)](https://docs.stripe.com/billing/subscriptions/usage-based-legacy).

**UNVERIFIED / DOES NOT EXIST (as named)** — I found no `credit_price` field and no `usage_future` value anywhere in the Checkout/Subscription/Price/Meter API reference or the OpenAPI spec. The nearest real things: `recurring.usage_type` ∈ `metered` | `licensed` (metered prices), meter-event **credits** (`billing.credit_grants`, credit balance), and `pending_invoice_item_interval` / `billing_thresholds` (when accrued usage gets invoiced). Treat `credit_price`/`usage_future` as non-existent names in current Stripe docs.

**Recommendation (INFERENCE)** — for platfolio:
1. Start with **flat-rate plans** (per-seat/per-plan prices) — that matches the "we absorb Railway cost" managed model, avoids the meter's invoice-time-only visibility, and keeps Checkout/portal/tax all working.
2. Add **Meters** (not Metronome) only if you must pass through per-tenant infra consumption, because Metronome currently breaks **Connect** and Dashboard/Workflows and needs a Metronome sandbox + rep. Railway's own metering is per-second (`memory $0.00000386/GB/s`, `CPU $0.00000772/vCPU/s`, `volumes $0.00000006/GB/s`, `egress $0.05/GB` — [railway.com/pricing](https://railway.com/pricing)), so a `sum` meter with `event_time_window=hour` and one meter event per tenant per hour (identifier = `tenant:period:hour`) is a clean, low-cardinality design; late events beyond 35 days must be handled by your own reconciliation + `meter_event_adjustments`.
3. Never rely on meters for "credit on cancellation": *"If you don't prorate the subscription, all metered usage gets discarded"* — so cancel flows must use `prorate=true`/`invoice_now=true` or bill final usage explicitly.

## 4. Selling a service vs reselling someone else's capacity (merchant of record)

### 4.1 Model A — platfolio bills the end customer in its own name (no Connect)

**VERIFIED** — everything in §1–§3 applies unchanged on your own Stripe account: standard `Customer`/`Account` + `Subscription` + `Invoice` + Checkout + Entitlements + Meters + Stripe Tax. Stripe's [MoR definition](https://docs.stripe.com/connect/subscriptions): *"the legal entity responsible for facilitating the sale of products to a customer that handles any applicable regulations and liabilities, including sales taxes."* In model A platfolio **is** the MoR: the customer's bank statement, invoice, refund path and tax liability are platfolio's. Stripe processing fee for domestic cards: **2.9% + 30¢** ([stripe.com/pricing](https://stripe.com/pricing)).

**INFERENCE** — this is the correct model *only if* you can lawfully buy the infra you resell. Railway's AUP (below) forbids exactly that shape on a platfolio-owned account, so model A works for the *software/support/managed-service* subscription, but the underlying Railway account must be the customer's (or a Railway-sanctioned arrangement).

### 4.2 The Railway constraint (this is the real driver, not Stripe)

**VERIFIED** — [Railway Acceptable Use Policy](https://railway.com/legal/acceptable-use) (also served as [Markdown](https://railway.com/legal/acceptable-use.md)) prohibits, verbatim: *"for other abuse of the platform, including **cryptocurrency mining, torrenting, reselling compute resources**, **evading usage or billing limits**, operating proxies or anonymization services, or running bots or scrapers that violate applicable terms of service"*, plus illegal content, NCII/harassment, fraud/phishing, pirated software, unauthorized access/malware/DDoS infrastructure, and unsolicited bulk messages. Enforcement: *"Railway may investigate any suspected violation…, and remove or disable access to any content or resource"*, and it will weigh *"your policies and processes you have in place to prevent or identify and remove any prohibited content or activity."* Closing line: *"If you are unsure whether your use case is allowed, **ask us before deploying**."*

**VERIFIED** — [Railway ToS](https://railway.com/legal/terms): *"You are responsible for what you host on Railway"*; the restrictions list includes *"…or that otherwise interfere with the proper working of the Services (including by **placing an unreasonable load on the Services' infrastructure**)"* and *"A violation of any of the foregoing is grounds for termination of your right to use or access the Services"*; Railway *"may suspend or discontinue any part of the Services… or impose limits"*, *"remove any Content… at any time, for any reason… and without notice"*, and *"is also free to terminate (or suspend access to) your use of the Services or your account for any reason in our discretion"*; DMCA policy with a named Designated Agent (Railway Corporation, Attn: DMCA Designated Agent, 548 Market St PMB 68956, SF CA), counter-notice, material *"may be replaced or access to it restored in 10 to 14 business days"*, repeat-infringer termination; charges/fees *"are your sole responsibility"*; account deletion stops display and deletes source-code submissions but *"it may not be possible to completely delete content from Railway's records"*. **Terms also exist as `https://railway.com/legal/terms.md`.**

**VERIFIED** — Railway's sanctioned routes for platfolio-shaped businesses:

## 6. Data deletion / GDPR when you host customer workloads

Roles: platfolio is a **processor** for its business customers (controller) and a **controller** for its own account/billing data. Railway (and AWS etc.) is platfolio's **sub-processor**. Stripe is platfolio's payment-data processor.

**VERIFIED — statutory anchors** ([EUR-Lex, Regulation (EU) 2016/679](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32016R0679)):
- **Art. 28(2)**: *"The processor shall not engage another processor without prior specific or general written authorisation of the controller. In the case of general written authorisation, the processor shall inform the controller of any intended changes concerning the addition or replacement of other processors, thereby giving the controller the opportunity to object."*
- **Art. 28(3)(g)**: the contract must stipulate that the processor *"at the choice of the controller, **deletes or returns all the personal data to the controller after the end of the provision of services** relating to processing, and **deletes existing copies** unless Union or Member State law requires storage of the personal data."*
- **Art. 28(3)(h)**: make available information + *"allow for and contribute to audits, including inspections."*
- **Art. 17(1)**: erasure *"without undue delay"* on the listed grounds.
- **Art. 12(3)**: respond *"within one month of receipt of the request. That period may be extended by two further months where necessary…"* with reasons given within the first month.
- **Art. 20(1)**: portability — *"in a **structured, commonly used and machine-readable format**"*, transmitted to another controller *"without hindrance"*.
- **Art. 32(1)**: security of processing (pseudonymisation/encryption, CIA/resilience, availability restoration, testing).

**VERIFIED — backups may outlive the live copy, if you say so and take them out of use** ([ICO, Right to erasure](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/individual-rights/right-to-erasure/) — the site blocks direct fetching, so this was read via a [Wayback snapshot](https://web.archive.org/web/2024/https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/individual-rights/right-to-erasure/)): *"If a valid erasure request is received and no exemption applies then you will have to take steps to ensure erasure from **backup systems** as well as live systems. Those steps will depend on your particular circumstances, your **retention schedule** (particularly in the context of its backups)… You must be **absolutely clear with individuals** as to what will happen to their data… It may be that the erasure request can be instantly fulfilled in respect of live systems, but that the data will remain within the backup environment for a certain period of time until it is overwritten. The **key issue is to put the backup data 'beyond use'**, even if it cannot be immediately overwritten. You must ensure that you do not use the data within the backup for any other purpose, ie that the backup is simply held on your systems until it is replaced in line with an established schedule."*

**VERIFIED — market practice to copy**
- **Stripe DPA** ([stripe.com/legal/dpa](https://stripe.com/legal/dpa)): §3.1(h) *"at User's choice, delete or return to User all Personal Data… and delete existing copies, following termination…, except that Stripe will not be required to delete… to the extent that Stripe's storage… is (i) required by Stripe to exercise its rights and perform its obligations under this Agreement; or (ii) required or authorized by DP Law for a longer period"*; §3.2(b) sub-processors: *"If User subscribes to email notifications at the **Stripe Sub-processors List**, then Stripe will notify User via email if Stripe intends to add one or more Sub-processors… at least **30 days before** the changes take effect. User may reasonably object… within **30 days**"* (objection remedy: Stripe may terminate; the list page is linked from the DPA — I did not fetch it, so its URL is UNVERIFIED); Art. 32-style controls listed (database replication, backup procedures, hardware redundancy, DR plan; disclosure controls).
- **Railway DPA** ([railway.com/legal/dpa](https://railway.com/legal/dpa)): *"Upon the termination or expiration of the Agreement, at Customer's choice, Company shall return or delete Personal Data, unless further storage… is required or authorized by applicable law. If return or destruction is **impracticable or prohibited**… Company shall take measures to **block** such Personal Data"*; SCC deletion **certification provided "only upon Customer's request"** (Clause 8.1(d)/8.5); sub-processors: *"**At least ten (10) days** before enabling any third party… Company will add such third party to the List and notify Customer via email"*, objection window **10 days**, list on trust.railway.com with optional notification subscription; *"**Railway purges or anonymizes customer data and customer content when a customer deletes their Railway account**"*; *"All customer data is backed up **daily**…"*; SCCs = Commission Decision 2021/914, plus UK Addendum / DPF; customer bears audit cost; duration: *"as long as required (i) to provide the Services…; (ii) for Company's legitimate business needs; or (iii) by applicable law."*
- **Render** ([render.com/terms](https://render.com/terms)) as a cautionary example of the "no promise" style: data *"may be deleted, altered, moved or transferred at any time for any reason in Render's sole discretion, with or without notice and with no liability of any kind"* — platfolio can differentiate by promising the opposite, in writing.

**UNVERIFIED** — a specific regulator-approved deletion-SLA number (none exists; "without undue delay" + one-month response is the only statutory clock); Railway's concrete post-deletion retention period (its ToS only says complete deletion "may not be possible"); Heroku's data-retention page (404 today).

**What an honest "eject / export-before-delete" flow must contain (INFERENCE)**
1. **Two distinct promises**, both dated: (a) *live* deletion within N days after termination (e.g. 14–30 days), (b) *backup/DR copies* age out on a fixed schedule (e.g. 90 days), are encrypted, are never restored into a live tenant environment for a terminated tenant, and deletion is certified on request (Railway/Stripe precedent for "on request").
2. **Export package, machine-readable and self-hostable**: config-as-code dump of the stack (services, env vars, domains, replicas, volumes), database dumps (SQL `pg_dump` custom + CSV, plus restore instructions), object-storage listing/manifest (or a bucket-sync recipe), volume archives (tar.zst with checksums), TLS/secret inventory *listed but not dumped* (secrets exported only with explicit re-auth; document which secrets rotate), logs/metrics export window, and the app's own source (usually already in the customer's repo). Format: JSON/YAML + `.tar.zst` + `SHA256SUMS`, with a `README-restore.md`. Aim: importable by **Coolify/Dokploy/CapRover/compose** so "take over your own infra" is a documented path, not a sales claim.
3. **A grace period with the tenant frozen, not destroyed**: read-only/`paused` state (Stripe `pause_collection` / `subscription.paused`, Railway scaling to zero), an explicit countdown e-mailed at day 0/7/21, a one-click extension, and a "hard delete now" opt-in for privacy-driven customers (Art. 17 erasure cannot wait on your retention schedule if no exemption applies).
4. **Process/sub-processor honesty**: keep a public sub-processor list with the 30-day-notice convention (Stripe-style) and a named EU representative/DPO mailbox; state which data (if any) is *not* deleted (billing records for statutory retention — cite the legal basis, since Art. 28(3)(g)/17(3)(b) allow it).
5. **Evidence trail**: log every export/suspend/delete event per tenant; make it quotable in an audit request.

### Recommended licensing scheme for platfolio (INFERENCE / proposal)

Three-layer, mirroring Dokploy's structure with Sentry's change-date safety valve:

1. **Control plane (`platfolio/` core, the thing you sell hosting against) → BUSL-1.1-style or FSL-1.1, with an `Additional Use Grant`/`Permitted Purpose` written for your actual customers.**
   - Grant: *"You may make production use of the Licensed Work for **internal purposes** and for provisioning hosting for your **own** workloads or your own clients' workloads, provided you do **not** offer the Licensed Work to third parties on a hosted or embedded basis **as a managed hosting/PaaS service that competes with platfolio's managed service**."*
   - Copy the BSL definitions of "competitive offering"/"Product"/"Embedded" verbatim (they are the best-drafted anti-hyperscaler language and explicitly say that a *non-paid* offering isn't competitive, and internal use isn't competitive — which protects self-hosters and agencies).
   - **Change Date: 24 months per release; Change License: Apache-2.0** (Sentry uses 2 years → Apache-2.0; HashiCorp uses 4 years → MPL-2.0). This keeps you credible as "open" while deferring the free-riding window.
   - Note honestly in the README: **source-available, not OSI open source** (BSL/FCL/SSPL/ELv2/RSAL are not open-source licences). Do not call platfolio "open source" without that caveat; that's the reputational trap n8n/Elastic/Redis all hit.
2. **Everything a customer ships → Apache-2.0 (or MIT) and explicitly excluded from layer 1.** Directories: `templates/`, `stacks/`, `blueprints/`, `sdk/`, `agent-runtime/` (the per-workload sidecar the customer runs), each with its own `LICENSE` file + a root statement in the Dokploy/GitLab idiom (*"Content under X/ is licensed under Apache-2.0 as defined below…"*). Reason: (i) a customer who ejects to Coolify/Dokploy/plain Docker must not inherit a hosting restriction on *their* app; (ii) a permissive sidecar keeps the anti-competition restriction inside the control plane, which is where you can actually enforce it and where the value lives.
3. **Binaries must stay redistributable.** Under BUSL/FCL the licence *is* the source-available text, so plain binaries distributed alone would be a grey zone. Fix it contractually and technically:
   - publish the **corresponding source for every released binary** (build reproducibility + a `SOURCE` link or embedded build-id in the artifact), so the source-available licence always covers the binary;
   - make the redistribution duty explicit and light: *"You may copy, publish and redistribute unmodified copies of the Licensed Work, including compiled binaries, provided you (a) include the full license text or a link to it, (b) do not remove notices, (c) do not rebrand it as your own service, and (d) your distribution is not itself a competing managed offering."* (Sentry's Redistribution clause is exactly this, minus (d); BSL's "Provide"/"Embedded" definitions let you draw (d) cleanly.)
   - This is what makes *"brew install / download the CLI and run platfolio locally"* legal for a stranger while *"platfolio-as-a-service by CloudCo"* requires a commercial agreement.
4. **Trademark & branding policy alongside it (mandatory, not optional).** Precedents to copy: FSL's Trademark clause (*"you have no right … to use our trademarks, trade names, service marks or product names"* except to identify origin) and [GitLab's Trademark Guidelines](https://handbook.gitlab.com/handbook/marketing/brand-experience/trademark-guidelines/) which explicitly permit *descriptive* use — *"This product is an issue downloader for GitLab"*, and *"[Your brand name] managed service for GitLab"*, provided it doesn't create *"a likelihood of confusion as to the origin"* or imply affiliation, and the mark is **not the first word** of a plugin/extension name, with logos reserved. Concretely for platfolio: (a) publish a trademark policy page + a logo/usage kit; (b) state that forks must rename ("platfolio-compatible" naming rules: no "Platfolio" as first word, `for platfolio` suffix allowed, no logo reuse, no implying endorsement); (c) reserve the name for the hosted service; (d) give an explicit *compatible-distribution* allowance so package managers/Linux distros aren't scared off — that is what the GitLab/OpenSearch episode teaches: AWS had to rename *Amazon Elasticsearch Service → [Amazon OpenSearch Service](https://aws.amazon.com/blogs/opensource/introducing-opensearch/)* precisely because the trademark, not the code, was the scarce asset.
5. **Optional add-on, cheap and precedented**: an `ENTERPRISE.md`/`/proprietary` directory (Dokploy) for SSO/SCIM/audit logs/white-label, and an **agency/partner licence SKU** (Dokploy's Agency plan, Coolify's team subscriptions) — because platfolio's channel is agencies, and a named licence beats grey-area OEM use.
6. **Open-core escape hatch if community credibility matters more than the moat**: MIT core + `/proprietary` (GitLab/Dokploy) or AGPL-3.0 core (Gitpod/Elastic-triple) — AGPL gives you copyleft against closed forks but does **not** stop a competitor from running the service and publishing changes, and is the choice most likely to make an enterprise procurement team say no. That trade-off is a business decision, listed in §8.

## 8. Decisions you must make, in Stripe terms

1. **Merchant of record** — platfolio (Standard Billing, 2.9%+30¢, you own tax registration/filing + refund/dispute liability), or **Stripe Managed Payments** (Stripe as MoR, +3.5%, tax registered/filed/remitting in 80+ countries) — and note MoR is *mutually exclusive with Connect*, requires subscriptions created only via Checkout/Payment Links, and forbids ad-hoc invoice items/one-off invoices. Decide before you design the invoice pipeline, because usage pass-through cannot live inside Managed Payments.
2. **Metered vs flat (and who owns the infra bill)** — flat per-plan prices (simplest, keeps Checkout/portal/tax intact) vs metered per-tenant Railway usage via **Billing Meters** (not Metronome, because Metronome currently has no Connect support and limited Checkout). Sub-decision: **does the customer pay Railway directly or platfolio?** If Railway bills the customer (Railway OAuth app or Stripe APP/`stripe projects add railway/hosting`), platfolio sells only a software/management subscription — no Connect, no reselling-compute AUP problem, no usage pass-through, much lower margin risk. If platfolio pays Railway and resells, you need Railway's written permission first (their AUP bans reselling compute) or an Enterprise agreement.
3. **Entitlement source of truth** — adopt Stripe **Entitlements** (`entitlements.feature` + `lookup_key` + `entitlements.active_entitlement_summary.updated`) as the authority for *which features*, with a thin local `lookup_key → limits` table for *how much*; or stay with your own plan/entitlement table keyed off `Price.id`/`Price.lookup_key`. Do not split authority: pick one and have the control plane read only that. Also decide `Customer` vs **Accounts v2** customer-configured `Account`, and `billing_mode=classic` vs **`flexible`** (irreversible one way; flexible changes proration credits, zero-usage line items and the metered price-at-report-time rule — choose flexible and `2026-09-30.endive` if you want Trial Offers).
4. **License + brand** — (a) BSL-1.1/FSL-1.1 for the control plane with a written Additional Use Grant for self-hosters and a 2-year Apache-2.0 change date, **vs** MIT/Apache open core with `/proprietary` (Dokploy-style) **vs** AGPL-3.0 (Gitpod-style); (b) Apache-2.0 for `templates/`, `blueprints/`, `sdk/`, per-workload runtime — confirm this is a decision, not an accident; (c) binaries: commit to publishing corresponding source per release so redistribution stays licensed; (d) publish a trademark policy (name rules + descriptive-use permission like GitLab's "managed service for X") and reserve "platfolio" for the hosted service.
5. **Retention promises** — live-data deletion window, backup age-out schedule ("beyond use", per ICO), and the eject package contents; mirror Stripe (30-day sub-processor notice) or Railway (10-day) as your own customer-facing notice period.
